# M2.0-P2-E1 持久化报告

- 阶段：M2.0-P2-E1
- 结论先行：**本阶段完成了科技进度的持久化边界、纯 JSON 状态模型、序列化/恢复接口与容错测试；没有、也不应该在 E1 新建临时存档系统**（项目至今没有任何存档实现，SAVE-ARCHITECTURE 仍是设计）。科技进度目前**仅存在于会话内**，刷新即丢失——这一点在验收中被明确声明，不伪装成已完成。

---

## 1. 现有持久化现状（事实）

| 检查 | 结果 |
|:--|:--|
| 游戏存档/读档模块 | 不存在（`assets/` 无 save/load/persist/serialize 实现） |
| 存储调用 | 不存在（无 localStorage/indexedDB/storage 调用） |
| 版本/迁移 | 不存在（唯一 `version` 是 UI 协议版本） |
| 存档 UI/协议 | 不存在（UI 协议无 save/* 命令） |
| 平台能力声明 | `zaohua-platform-init.js` 仍是 `capabilities: []` |
| 既有方案 | `docs/design/SAVE-ARCHITECTURE.md`：14 类状态、6 个接口缺口、快照 v1 设计 |

---

## 2. 数据分类（哪些属于科技、哪些不属于）

| 类别 | 内容 | 是否持久化 | 理由 |
|:--|:--|:--:|:--|
| **静态科技定义** | 12 节点、前置图、交付表、解锁表、能力/项目 ID | ❌ 不进存档 | 编译期常量；版本随构建走；存档只存玩家进度，不存数据表 |
| **玩家科技进度** | `delivered`（每种材料已交件数）、`unlocked`（已完成节点）、`trackedId`（追踪目标）、`mode` | ✅ **必须存** | 丢失等于科技进度清零 |
| 派生状态 | 节点 locked/available/researching/completed、前置闭包、剩余材料、进度百分比 | ❌ 不存 | 由进度 + 静态定义重算，避免两份状态互相矛盾 |
| 世界状态 | 机器、零件、建筑、库存、动力源启停、矿点 | 属于既有系统 | 与科技分开；科技只依赖库存（交付时扣料） |
| 瞬时状态 | 交付进行中的 UI 选择、当前面板页签 | ❌ 不存 | 读档时回到默认 |

## 3. TechState 模型（v1）

```jsonc
{
  "version": 1,
  "mode": "player",              // player | legacy（legacy 仅测试启动配置）
  "delivered": {                 // nodeId -> itemId -> 已交付件数
    "tech:gear-manufacture": { "iron_ingot": 3, "shaft": 2 }
  },
  "unlocked": ["tech:gear-manufacture"],   // 已完成节点（派生可算，显式保存便于校验）
  "trackedId": "tech:chute-logistics"      // 可为 null
}
```

- 纯 JSON：无 Map/Set/类实例/实体句柄，可直接 `JSON.stringify`。
- 无冗余状态：节点四态、前置闭包、剩余材料都不存。
- 未知节点/物品不导致整包失败（逐条丢弃并记录）。

---

## 4. 接口

| 接口 | 语义 |
|:--|:--|
| `tech.serialize(): TechState` | 返回可序列化副本（防御性拷贝，外部改不到内部） |
| `tech.restore(raw): { state, repaired, issues }` | 从不可信数据恢复；返回是否修复与修复记录 |
| `tech.snapshot(): TechSnapshot` | 只读快照（唯一 GameRead 的 `tech` 字段） |
| `TechState.version = 1` | 版本随快照走；迁移入口已预留 |

**尚未接入**：存储通道（`platformSdk.storage` / devStub）、保存触发（debounce/visibilitychange/手动）、存档 UI、读取时序（进入世界后 restore）。
这些属于存档 P0 的范围，E1 不越界实现。

---

## 5. 容错、版本迁移与幂等

| 场景 | 处理 |
|:--|:--|
| `version` 不符 | 保留可识别字段、记录 issue，不整包拒绝 |
| 未知节点 ID / 未知物品 ID | 逐条丢弃 + 记录 |
| 负数 / 小数 / 超过需求 | clamp 到 `[0, 需求]`，记录修复 |
| 已解锁但前置未完成 | 按前置闭包反复剔除（多级），记录修复 |
| `trackedId` 未知 | 置 null |
| 重复 `restore` | 结果相同（幂等） |
| 交付重复完成 | `completed` 节点拒绝提交；计数上限保护 |
| 交付后读档 | 以进度为准，不重放交付（材料不返还） |

对应测试：`tech-persistence.test.ts` 19 例（往返相等、防御性拷贝、版本/未知/负值/超额、闭包多级修复、trackedId、幂等）。

## 6. 与未来存档的集成约定（给 P0 / E3）

1. **位置**：快照 v2 增加 `tech` 字段，值 = `tech.serialize()`；不新增存档文件。
2. **顺序**：库存/快捷栏 → 建筑 → 机械 → **科技**（科技只依赖静态数据与自身进度，不依赖世界几何）。
3. **保存时机**：拓扑/库存变化后 debounce 5 s（既有方案）、科技交付成功后**立即标脏**、页面隐藏时保存。
4. **读取时机**：世界服务就绪后调用 `tech.restore(snapshot.tech)`，再广播 UI/GameRead。
5. **失败策略**：restore 返回 `repaired=true` 时仍继续（逐条修复），只有整包不可解析才回退初始状态并提示。
6. **禁止**：不允许 UI 直接改科技状态（只读快照）；不允许存档绕过交付校验（restore 只恢复已发生的进度）。
7. **迁移**：科技 `version` 独立于存档 `version`；任一变化都要保留「未知字段丢弃、已知字段修复」的行为。

## 8. 结论

- 科技进度的**数据模型、边界与恢复契约**已经完成并通过 19 例容错/幂等测试；
- **没有新建临时存档系统**，避免与未来 SAVE-ARCHITECTURE 不兼容；
- 当前玩家刷新会丢失科技进度，这是 E1 的已知限制，必须在 E2 验收与 P0 排期中显式处理；
- 若 E2 需要在无存档的情况下演示，建议只在验收说明中标注「会话内进度」，不得声称已持久化。
