1. 不新增第二个 GameRead；科技可读状态并入 `mechanical` 唯一 read。
2. 不新增机器和物品（本轮设计）；科技只解锁**已有内容的获取与组合能力**。

4. 拆除/回收语义保持"精确一次返还"，否则经济闭环会被玩家利用。
5. 既有验收脚本（M1.8 / M2.0-P1 / P2-B / P2-C / P2-D 共 6 条 playthrough）依赖
   "开局套件 + 全部配方"，替换原型供给必然影响它们——这是 P2-E1 的显式工作量（见 §12）。

## 2. 技术阶段定义

Demo 覆盖 **3 个技术阶段 + 1 个教学阶段**。阶段 0 不消耗科技进度，是既有订单的教学段。

| 阶段 | 名称 | 玩家身份变化 | 主要新增能力 | 结束时玩家能做什么 | 目标时长 |
|:--|:--|:--|:--|:--|--:|
| 0 | 手工工坊 | 被留下的学徒 | 无（既有 8 步教学订单） | 手摇动力 → 破碎 → 熔炼 → 锻出第一根传动轴 | 8–12 min |
| 1 | 基础工业 | 工坊主人 | 齿轮制造、溜槽物流、跨层传动、输入接口盒 | 扩建动力网络、让机器之间自动送料 | 18–25 min |
| 2 | 机械化生产 | 车间管理者 | 输出接口盒、物料连接、分流/合流、核心复制、飞轮制造、结构框架/组合机械 | 搭多核并联/串联产线，用组合机械组织车间 | 28–38 min |
| 3 | 初级自动化工业 | 工厂主 | 批量加工配方、组合产线诊断、联合工厂终局项目 | 建一条"多级加工 + 多机协作 + 组合机械"的完整产线并交付成套设备 | 30–45 min |

合计目标体验时长 **85–120 分钟**（与 Demo 定位一致）。

### 2.1 两条技术路线

**机械动力路线（P）**：把"能量怎么来、怎么传、怎么用"一点点展开。

```
手摇储能（已实现，阶段0）
  └─ 基础传动扩建（轴/齿轮可再造）        T1.1
       ├─ 跨层传动（立式传动带可造）       T1.3
       │    └─ 飞轮制造（第二动力源）      T2.4
       │         └─ 组合机械（结构框架）   T2.5  ← 与工业路线交叉
       └─ （未来）风力 / 水力 / 蒸汽 —— Demo 不实现
```

**工业制造路线（I）**：把"物料怎么加工、怎么流动、怎么组合"一点点展开。

```
基础加工（破碎/熔炼/锻轴，已实现，阶段0）
  └─ 溜槽物流（机器→机器）              T1.2
       └─ 输入接口盒（溜槽自动进料）      T1.4
            └─ 输出接口与物料连接         T2.1
                 ├─ 分流/合流             T2.2
                 ├─ 加工核心批量制造       T2.3
                 │    └─ 批量加工配方      T3.1
                 │         └─ 多级产线整合 T3.2
                 └─ 结构框架/组合机械      T2.5 ← 与动力路线交叉
                      └─ 联合工厂总成      T3.3（终局）
```

### 2.2 交叉关系（两条路线如何咬合）

| 交叉点 | 工业路线需求 | 动力路线需求 | 交叉后的玩法变化 |
|:--|:--|:--|:--|
| T2.5 组合机械 | 已能造输出/合流盒与结构框架 | 已能造第二台飞轮、已能跨层传动 | 多台核心被组织成一个"车间"，整体选择/边界可见；组合本身不增加产能，但让多机产线的组织与拆解成为可管理对象 |
| T3.2 多级产线 | 已能复制核心、已能批量加工 | 动力足够驱动 5–7 台机器 | 玩家第一次面对"动力预算 vs 机器数量"的取舍（飞轮 140 扭矩不够时要么减机、要么加源、要么换齿轮比） |
| T3.3 联合工厂 | 交付成套设备（含机械产品） | 交付的设备必须由玩家自己造的机器生产 | 终局目标同时验证两条路线 |

> 设计上不强制线性：T1.2 与 T1.3 可互换顺序，T2.2/T2.3/T2.4 可并行推进。
> 只有跨阶段节点（T2.5、T3.2、T3.3）要求两条路线同时到位。

## 3. 科技数据模型

### 3.1 稳定 ID 规范

沿用工业层既有 ID 规范（`assets/industrial/ids.ts`）：**只追加，不改名**。科技节点 ID 形如
`tech:<kebab-slug>`，一经发布不得复用；节点内引用的物品/配方/机器/端口/结构一律复用
已有稳定 ID（`ItemId`、`RecipeId`、`PartId`、`PortModuleId`、`StructureModuleId`），
禁止为科技树另造平行 ID。

> ID 校验注意：现有 `assertStableId` 的 `STABLE_ID_PATTERN` 只接受 `.` 与 `-`
> （`assets/industrial/ids.ts:20`），不含 `tech:` 前缀。P2-E1 必须二选一定案：
> ①新增 `TECH_ID_PATTERN`（允许 `tech:` 前缀，与运行时 `link:`/`assembly:` 风格一致），
> 或 ②改用 `tech.<slug>`。本文档统一写 `tech:<slug>`，实现时按①处理；
> 科技 ID 不得直接交给 `assertStableId` 校验。

### 3.2 节点定义（建议的数据形状，P2-E1 实现）

```ts
type TechStage = 1 | 2 | 3;
type TechRoute = 'power' | 'industry' | 'cross';

interface TechCostEntry { readonly itemId: ItemId; readonly count: number; }

type TechUnlock =
  | { readonly kind: 'recipe';    readonly id: RecipeId }
  | { readonly kind: 'machine';   readonly id: PartId }        // 允许制造/放置该机器
  | { readonly kind: 'port';      readonly id: PortModuleId }  // 允许制造/安装该接口盒
  | { readonly kind: 'structure'; readonly id: StructureModuleId }
  | { readonly kind: 'power';     readonly id: 'flywheel' }
  | { readonly kind: 'capability'; readonly id: 'material-link' | 'split-merge' | 'assembly' | 'line-diagnostics' }
  | { readonly kind: 'project';   readonly id: 'combined-works' };

interface TechNodeDef {
  readonly id: string;                 // 'tech:gear-manufacture'
  readonly name: string;               // 齿轮制造
  readonly stage: TechStage;
  readonly route: TechRoute;
  readonly purpose: string;            // 玩法目的（一句话）
  readonly requires: readonly string[]; // 前置节点 ID
  readonly cost: readonly TechCostEntry[];
  readonly unlocks: readonly TechUnlock[];
}
```

设计约束：节点定义是**纯数据、零引擎依赖**（与 `order.ts`、`recipes.ts` 同风格），
校验器检查：ID 唯一、前置存在且无环、成本物品存在且数量 > 0、解锁目标存在。

### 3.3 节点状态机

| 状态 | 含义 | 进入条件 | 退出条件 |
|:--|:--|:--|:--|
| `locked` 未满足前置 | 面板灰显，可查看不可操作 | 前置未全部 `completed` | 前置全部完成 → `available` |
| `available` 可研究 | 面板高亮，可交付 | 前置完成且自身未完成 | 首次提交任意材料 → `researching` |
| `researching` 研究中 | 已有部分材料入库，进度条显示 | 已提交材料 > 0 且未集齐 | 集齐 → `completed` |
| `completed` 已解锁 | 节点封存，不可再交付 | 全部成本集齐（提交瞬间原子完成） | 不可逆 |

- 状态是**派生**而非独立存储：`locked/available` 由前置闭包推导，`researching/completed`
  由已提交材料与成本比较推导。持久化只需保存"已提交材料"和"已解锁集合"。
- 无"研究计时器"：交付即解锁，避免玩家站着等进度条。研究中状态由"部分交付"体现。
- 完成判定在提交事务内一次完成：集齐最后一件的同一帧置为 `completed` 并广播解锁。

```
T1.1 齿轮制造 ──┬─▶ T1.2 溜槽物流 ──▶ T1.4 输入接口盒 ──▶ T2.1 输出接口与连接
                │                                              ├─▶ T2.2 分流与合流
                │                                              ├─▶ T2.3 核心批量制造 ──▶ T3.1 批量加工 ──▶ T3.2 多级产线整合 ─┐
                └─▶ T1.3 跨层传动 ──▶ T2.4 飞轮制造 ──┐        └──────────────────────────────────────────────────────────────┴─▶ T3.3 联合工厂总成（终局）
                                                      └─▶ T2.5 结构框架/组合机械 ─────────────────────────────────────────────┘
```

依赖图规则：**不允许"跨阶段跳跃"**（阶段 2 节点不得以阶段 3 节点为前置），

## 5. 科技解锁原则

### 5.1 解锁对象的四类语义（必须区分）

| 语义 | 例子 | 玩家实际获得 | 代码对应 |
|:--|:--|:--|:--|
| **解锁能力** | 物料连接（`J`/`H`）、`P` 结构模式、分流安装（`K`） | 交互从"无效/提示未解锁"变为可用 | 门控函数 `tech.isUnlocked(capability)` |
| **解锁配方（图纸）** | `forge-gear-12`、`forge-crusher`、`forge-flywheel` | 锻压机 `R` 循环里出现该配方；仍需自己备料、自己造 | 配方过滤 `recipesFor` |
| **解锁机器可制造性** | 破碎机/熔炼炉/锻压机可被制造 | 只能通过配方生产，**不会免费发机器** | 机器可用性 + 配方双门控 |
| **解锁结构与模块** | 结构框架配方 + `P` 模式；4 种接口盒安装 | 需自己制造模块再安装 | `structure`/`port` 门控 |

### 5.2 明确不做的事

- **科技解锁 ≠ 免费发放机器**：任何节点都不直接往背包塞机器或接口盒。
- **科技解锁 ≠ 物品来源**：物品只能来自采集（铁矿石）、加工（碎铁矿/铁锭/零件）、
  制造（锻压机）三条路径；科技只打开"能不能造/能不能用"，不打开"白给"。
- **市场采购不属于本 Demo**：工业市场（P2-F）未来只允许购买**基础材料**（如铁矿石/铁锭），
  不允许购买科技锁定物、不允许跳过交付。市场与科技树的关系在本设计中只留接口边界（§9.3）。
- **未实现的东西不能写进解锁**：风力/水力/蒸汽、传送带、电力只作为"未来节点"（§10），
  不进入 Demo 的 12 个节点。

### 5.3 门控点（实现位置，来自调查）

| 层 | 门控点 | 现状 |
|:--|:--|:--|
| 配方 | `recipesFor(partId)` 返回整表；`activeRecipe/cycleRecipe` 无过滤 | 需在此层按已解锁集合过滤（保留配方索引稳定性：解锁集合外的配方不参与 R 循环） |
| 机器 | `partDefForItem`、`place()`、`PROTOTYPE_KIT`/槽位绑定 | 需在放置与套件发放处按已解锁机器过滤 |
| 端口 | `PORT_MODULES` + `installModule` / `PortRuntime.install` | 需按已解锁模块 + 能力过滤 |
| 结构 | `STRUCTURE_MODULES` + `placeFrameAt` / `structurePlacementIssue` | 需按已解锁结构过滤 |
| 阅读/UI | 唯一 GameRead `mechanical` → 增加 `tech` 字段 | P2-E1 完成 |
| 进度 | 新 `tech` 服务（节点状态/交付事务/追踪） | P2-E1 新建 |

## 6. 科技交付机制

### 6.1 交付从哪里提交

**复用现有 DOM 模态，不新增世界物体。** 科技面板作为 `Tab` 背包模态的第二个标签页
（"背包 / 科技"），玩家在科技页选中节点 → 右侧详情 → 逐项提交材料。

理由（基于现状）：
- 当前没有"向某处提交物品"的任何交互（无商店/收购站/箱子/任务提交点），从零造一个世界交付点
  要新增机器或建筑，违反"不扩大机器与物品数量"。
- 背包模态已经具备暂停、DOM 渲染、拖拽、焦点管理，且已有"打开即暂停"的成熟行为。
- 交付本质是"清点库存并扣除"，与 UI 位置无关；工业感来自"材料必须真实生产"，不来自动画。

### 6.2 交付流程与规则

| 问题 | 设计答案 |
|:--|:--|
| 如何选择目标节点 | 面板左侧按阶段分组列出节点；点击节点 → 右侧详情 + 交付区；已解锁节点只读展示 |
| 如何检查数量 | 交付区每行显示"需要 N / 拥有 M"（`inventoryCount` 实时刷新）；不足行禁用提交按钮 |
| 如何扣除物品 | 单物品**整批提交**：一次提交该物品剩余需求数量；事务顺序=先全量校验 → 再 `inventoryRemove` → 成功后写节点进度；任一步失败回滚 |
| 部分交付是否允许 | **允许**：按物品逐项提交（例如先交 3 铁锭，再交 2 传动轴）；每项提交后立即扣库存并计入该节点进度 |
| 已提交材料是否返还 | **不返还**（防刷、防反复横跳）。UI 在首次提交前提示一次"已提交材料不可退回，但进度会保留" |
| 集齐后如何解锁 | 最后一项提交成功的同一帧：节点状态置 `completed` → 应用解锁（配方/能力/模块）→ 广播 UI/追踪/提示 |
| 如何解锁后继节点 | 前置闭包在每次读取时重算：全部前置 `completed` 的节点变为 `available`；不需要显式"解锁后继"写入 |
| 重复交付/重复解锁如何防止 | ①已 `completed` 节点拒绝任何交付；②进度按 `(nodeId,itemId)` 计数且上限=需求；③提交事务幂等：同一帧重复提交只成功一次；④读档后按"已提交计数"重算，不重放交付 |
| 交付过程如何反馈 | ①行级：拥有数/需求数/按钮态；②节点级：进度条 + "研究中"状态；③解锁瞬间：完成横幅 + HUD 提示 + 追踪卡片更新；④错误：库存不足/节点锁定给出明确原因（复用 `resolveBlocker` 的 code+message 风格） |
| 是否需要交付点/距离限制 | Demo **不要求**玩家站在某处：面板内提交即可（避免"跑去交付台"的往返）。未来市场/交付点( P2-F )另行设计 |

### 6.3 事务边界（关键实现约束）

`inventory.ts` 只有**单物品整笔原子**（`has` + `remove`），没有多物品事务。因此：

1. 每行提交只涉及**一种物品**：`has(item,n)` → `remove(item,n)` → 写进度，天然原子。
2. "一键交齐"（可选便利功能）涉及多种物品：先对全部条目 `has` 预检，再逐条 `remove`；
   任一条 `remove` 返回 false 时，把已扣的条目 `add` 回去并报错（补偿事务）。
3. 进度写入必须**晚于**库存扣除成功；崩溃/读档后以"进度为准"而不是以"库存为准"重算（材料不返还）。
4. 不在 `inventory` 上加事务 API（避免动已验收系统）；事务封装在新 `tech` 服务内部。

### 6.4 与订单系统的职责边界

| 维度 | 教学订单（阶段 0，保留） | 科技树（阶段 1–3，新增） |
|:--|:--|:--|
| 目的 | 教玩家操作流程（采集→造机→接动力→生产→锻轴） | 驱动长期目标、解锁能力 |
| 判定 | 只读：按 `production.produced` 相对基线增量、8 步 latch | 交付：真实扣库存 + 前置闭包 |
| 是否扣材料 | 否 | 是（不可返还） |
| 状态机 | 既有 `goal.ts`（不回退、锁存） | 新 `tech` 状态机（locked/available/researching/completed） |
| UI | 左上订单 HUD（既有） | `Tab` 背包模态的科技页 + 左上科技追踪卡（订单完成后替换） |
| 复用 | — | 复用订单的"只读投影 + 阻塞文案 + 签名去重 + 面板模板"模式，不复用其状态机 |
| 关卡衔接 | 订单完成后 HUD 自动切到科技追踪 | 科技树第一个节点在订单完成前也可用（不强制等待） |

> 结论：**订单降级为教学与文案模板，科技树成为进度主系统**。既有 8 步订单的全部验收脚本
> （`m20-first-order.mjs`）在 P2-E1 必须继续通过（订单逻辑不改）。

### 7.2 节点状态可视化

| 状态 | 卡片 | 详情页 | 备注 |
|:--|:--|:--|:--|

### 7.3 HUD 追踪卡

- 位置：左上，订单 HUD 原来的位置（`left:16px; top:146px; width:302px`）。
- 内容：当前追踪节点名、阶段/路线标签、进度条（已交材料数/总件数）、最多 3 条缺失材料
  （"铁锭 1/3"）、一个"打开科技（Tab）"提示。
- 切换规则：教学订单未完成 → 显示订单 HUD；订单完成后 → 显示科技追踪卡。

- 布局约束：目标/HUD 面板与追踪卡互斥显示，复用同一块 302px 区域，避免 1280×600 下重叠。

### 7.4 数据与协议

- 唯一 GameRead `mechanical` 增加只读 `tech` 字段：
  `{ unlocked: string[], states: {id, status, delivered: Record<ItemId, number>}[], trackedId: string|null }`。
- UI 协议由 v1 → **v2**：`UiStateMessage` 增加可选 `tech` 字段；新增上行命令
  `tech/submit {nodeId, itemId, count}` 与 `tech/track {nodeId}`。
- 兼容：版本不匹配仍拒绝（现有协议行为不变）；v2 双端同版本发布；`parseState` 对 `tech` 缺失
  或畸形做防御式回退（不整包丢弃）。
- 面板渲染只读 `tech` 快照 + 库存快照；提交按钮发命令后等待下一帧状态刷新，前端不本地改状态。
- 性能：科技状态只在交付/追踪变化时改变签名，沿用现有`stateSignature` 去重，不每帧重算。

## 8. 进度与持久化

### 8.1 最小状态模型

```ts
interface TechState {
  readonly version: 1;
  readonly delivered: Record<string /* nodeId */, Record<string /* ItemId */, number>>;
  readonly unlocked: readonly string[];   // 已完成节点（可推导，但显式保存便于校验）
  readonly trackedId: string | null;
}
```

- 只保存"已提交材料计数 + 已解锁节点 + 追踪目标"三样；节点状态、前置闭包、进度条全部派生。
- 数量上限 = 节点需求；读取时逐项 clamp，避免篡改/迁移导致溢出。
- 未知 nodeId / itemId：逐条丢弃并计数（不整包拒绝），与 SAVE-ARCHITECTURE 的容错原则一致。

### 8.2 与存档的关系

- 当前**没有任何持久化**（`assets/` 0 行存储调用）。科技状态必须：
  1. 设计成纯 JSON（上面的 `TechState`）；
  2. 在存档系统落地时并入快照 `v2` 的 `tech` 字段（SAVE-ARCHITECTURE 已有版本位）；
  3. 在存档落地前，科技进度**仅存在于会话内**，刷新即丢——必须在 P2-E1 的验收说明中写明，
     并在 P2-E3 与存档 P0 合并验收。
- 快照顺序：库存/快捷栏 → 建筑 → 机械 → 科技（科技只依赖库存与节点数据，不依赖世界几何）。
- 迁移：`version` 不符时按"保留可识别字段、丢弃其余"处理；v1→v2 预留迁移函数位。
- 幂等：恢复时按已提交计数重算 `researching/completed`；重复交付由"completed 拒绝 + 计数 clamp"双重兜底。

### 8.3 防刷与防丢

| 风险 | 兜底 |
|:--|:--|
| 重复交付同一材料 | 需求上限 clamp + completed 拒绝 |
| 交付后退档刷材料 | 材料不返还 + 读档以进度为准（不重放交付） |
| 未知节点 ID（版本变化） | 逐条丢弃 + 日志计数 |
| 前置图数据错误（环/缺失） | 启动时校验器报错，禁用科技系统并提示（不崩游戏） |
| 未解锁却能造/能装 | 门控在运行时每帧查询，UI 只是显示；门控失效不会导致崩溃 |

### 9.3 市场边界（P2-F，不在本阶段）

- 市场只作为"材料补给渠道"，不承担科技解锁；科技树不依赖市场。
- 交付物不进入市场流通（防止"买齐材料直接解锁"绕过生产）。
- 科技面板的"提交"与市场交易是两套事务，不得互相调用。

### 9.4 回收与返还

- 拆机器/接口盒/结构框架沿用现有"精确一次返还"规则（`mechanical.pack.ts` / `port.pack.ts`）。
- 已交付给科技节点的材料**不返还**（与拆除返还区分：交付是消费，拆除是回收）。
- 读档后不重复返还（返还由实体存在性驱动，不是事件驱动）。

## 11. 数值与材料预算

### 11.1 现有供给（硬事实）

- 铁矿石：**4 矿点 × 20 = 80，不可再生**；破碎 1:1、熔炼 1:1 → 全流程最多 80 铁锭当量。
- 开局套件（现状）价值约 120+ 铁锭当量，免费发放——这正是"科技树没有意义"的根因。
- 新规则后开局套件约 35 铁锭当量的"继承设备"，其余靠生产。

### 11.2 三阶段材料预算（铁锭当量）

| 用途 | 数量 | 说明 |
|:--|--:|:--|
| 科技交付（12 节点合计，**已含 T3.3 成套设备 ≈38**） | ≈ **155** | 见各节点交付；不得与下一行重复计算 |
| 玩家自建机器（第二/第三核心、第二飞轮、传输件） | ≈ **40** | 多级产线至少 2 台额外核心 |
| 玩家损耗与容错 | ≈ **15** | 拆建、试错、齿轮 |
| **合计需求** | **≈ 210 铁锭当量** | 且不存在回收再投入的循环（交付不返还） |

**结论：当前 80 矿石（80 铁锭当量）不足以支撑 3 阶段 + 终局，缺口约 2.6 倍（80 → 210）。**

### 11.3 建议的供给调整（P2-E3 数值，需用户确认）

| 方案 | 内容 | 影响 |
|:--|:--|:--|
| A（推荐） | 矿点储量 20 → 50（4×50=200），另设 1 个"深层矿脉"节点 +50 | 总供给 250，匹配预算；改动仅世界数据 |
| B | 矿点数量 4 → 8（8×20=160），另加 1 个富矿点 40 | 总供给 200，略低于 210 预算，需压缩容错或节点成本；探索范围变大，地图 32×32 需重排矿点 |
| C | 矿石再生（每 120 s +1，上限 20/点） | 改变资源节奏，与"不可再生"的既有设计冲突，不推荐 |

> 若不调整供给，则必须把科技交付总量压到 ≈40 铁锭当量以内（相当于每个节点 3 铁锭），
> 科技树会退化成"点几下按钮"，与设计目标冲突。故 **供给调整是 P2-E 的前置决策**。

### 11.4 动力预算（阶段 3 的设计张力）

| 项 | 数值 | 说明 |
|:--|--:|:--|
| 单飞轮扭矩 | 140 N·m | 正式动力源 |
| 单飞轮能量 | 300 点；摇 45/s；耗 6 + 14×(demand/140)/s | 有储能上限，会耗尽 |
| 三核心负载 | 破碎 18 + 熔炼 24 + 锻压 22 = 64 | 阶段 2 一条线刚好 |
| 5 台机器 | ≈ 106 | 仍在一台飞轮能力内（但转速下垂明显） |
| 7 台机器 | ≈ 130 | 接近上限，必须加第二飞轮或换齿轮比 |
| 结论 | 阶段 3 的"多机 + 批量加工"必然撞到动力墙 | T2.4/T3.2 的存在意义 |

### 11.5 阶段时长目标

| 阶段 | 目标时长 | 关键节奏点 |
|:--|--:|:--|
| 0 教学 | 8–12 min | 第一次锻出传动轴 |
| 1 基础工业 | 18–25 min | 第一次自动送料（输入盒） |
| 2 机械化生产 | 28–38 min | 第一次多核产线与组合机械 |
| 3 自动化工业 | 30–45 min | 第一次批量产线与终局交付 |
| 合计 | 85–120 min | 与 Demo 演示目标一致 |
