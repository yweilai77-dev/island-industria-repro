## 2. P2-A 之后需要补查的链路

P2-A 已经查清物品/配方/加工/动力/运输/读投影的结构（见 `P2-A-INVESTIGATION.md`）。
P2-B 在此基础上补查了六条 P2-A 没细看、但本阶段必然改到的链路：

### 2.1 物品 → 图标 → 背包的完整链路

- `ItemDefinition.icon` 是**前端图标的键**，不是资源路径：`assets/frontend/icons.ts` 的
  `itemIconSvg(iconKey)` 用 `switch` 返回内联 SVG，未知键回退占位图。
- 背包/快捷栏 DOM 只读 `InventoryService.stacks()` + `itemIconSvg`（`frontend/frontend-ui.ts`），
  所以**新增物品只需改 `items.ts` + `icons.ts` 两处**，不需要动 HUD 结构。
- 结论：把接口盒做成真实物品是**可控的小改动**（但会打破「物品总数 = 14」的既有断言，需同步更新）。

### 2.2 手动投料路径（流槽之外的那条）

- `mechanical/runtime.ts` 的 `handleRightClick` / `KeyC`：
  - 右键：手上有非机械物品 → `production.insertInto(partId, itemId, 1)` → 扣库存；
    否则 `takeFrom` 取产物。
  - `KeyC`：悬停加工机器 → `production.loadFromInventory` 从库存取当前配方原料投 1 件。
- **两条都是直接写机器输入缓冲，完全不经过溜槽**。
- 结论：任务书 §2.3「新旧方式共存」在数据上是天然的——两条路径写同一个 `MachineState.inputCount`，
  不会有两套库存。

### 2.3 溜槽的自动路径（P2-B 必须切开的）

- ① 机器 → 溜槽：`ProductionRuntime.pushMachineOutputs`（产物沿本地 +X 推到相邻格）。
- ② 溜槽 → 下游：`handoff` 在 `t >= 1` 时按目标类型分派：溜槽 / 加工机器 / 末端进库存。
- 其中 ② 的「直接投进机器」正是任务书 §2.1 要禁止的行为；M1.8 已验收产线依赖它。
- **既有缺陷 A**：`markBlocked` 把物品钉在 `t = 0.92` 且 `blocked = true`，而
  `advanceChute` 对 blocked 物品只做 `t = min(0.92, t)`、`readyForHandoff` 又要求 `!blocked`；
  全仓**没有任何地方调用 `unblock`**。也就是说：溜槽一旦堵住，即使下游腾出空间也**永远不会恢复**。
  P2-B 要求「装/拆接口盒后自动输入恢复」，必须先修这个。

### 2.4 机器实体的拆除与返还

- `mechanical.pack.ts` 的 `remove(partId)`：注销空间 → 销毁视图 → 移出 registry → **把零件物品退回库存**。
- `ProductionRuntime.sync(parts)`：机器消失时 `flushMachine` 把输入/输出缓冲交回库存。
- 结论：接口盒作为「挂在机器上的状态」，必须在机器消失时同样 flush——挂到同一个 sync 语义上即可。

### 2.5 能否旋转已放置的加工核心

- 结论：**不能**。`R` 只在放置预览时旋转幽灵（`mechanical.pack.ts` 的 `let rotation`），
  放置后没有任何旋转入口；`updatePlacement` 服务存在但只暴露给未来阶段。
- 而验收要求 2.8 明确要「旋转加工核心时安装位与接口盒正确更新」，因此本阶段必须补一个旋转入口。

### 2.6 按键占用与输入冲突

已占用：`W/A/S/D`（移动）、`C`（摇柄/投料）、`F`（采集）、`G`（搬建筑）、`Q/E`（相机）、`R`（幽灵旋转 + 配方切换）、
`V`（楼层模式）、`X`（拆除）、`Delete/Backspace`（删选中零件）、`1-0 - =`（快捷栏）、`[ ]`、`Tab`、`Escape`。
可用：`T`、`Y`、`U` 等。P2-B 因此选 `T`（安装）/ `Y`（拆卸）/ `U`（旋转加工核心）。

**关键发现（既有缺陷 B）**：`R` 键被重载——mechanical 插件用它旋转放置幽灵，
mechanical-runtime 用它切换锻压机配方。按一次 R 会**同时**做两件事，玩家切完配方后
下一次放置会莫名转向。P2-B 的验收脚本因此必须自己记账（见报告 §7 的脚本说明）。

## 3. 必须由产品决定的两件事（已暂停并取得决定）

### Q1：自动输入的上游用什么？流槽的自动化职责何时终止？

调查事实：
- 游戏里**没有传送带**，唯一物料运输是重力溜槽；
- 溜槽同时在做「机器→溜槽」与「溜槽→机器」，M1.8 验收脚本 `m18c-production` 依赖后者；
- §2.1 字面上要求禁止溜槽自动进料，但溜槽**没有任何玩家手动交互**（手动投料是悬停机器按 C），
  若同时禁止两个自动方向，溜槽会变成完全无用的方块。

取得决定：**方案 P1** —— 接口盒成为唯一自动进料闸门：
保留「机器→溜槽」，取消「溜槽→机器直接进料」，改为「溜槽→已装接口盒→核心缓冲」；
没装接口盒的机器不再被溜槽自动喂料；手动按 C / 右键照常。
代价：M1.8 产线多一步「给熔炼炉装接口盒」，`m18c-production` 需同步更新（已按此执行）。

### Q2：要不要补「旋转已放置的加工核心」？

取得决定：**补，仅限加工核心**。轴/齿轮/动力源保持不可旋转，避免动到已验收的传动玩法。

## 4. 本阶段必须修的两处既有缺陷

| 编号 | 缺陷 | 为什么 P2-B 必须修 |
|:--|:--|:--|
| A | 溜槽堵塞后永不恢复（没人调 `unblock`） | 场景 E「拆卸后重新安装并恢复自动输入」不可能通过；且玩家会遇到「盒子满了→溜槽永远卡死」 |
| B | `R` 同时旋转幽灵与切配方 | 不影响游戏逻辑正确性，但会让「切完配方再放零件」莫名转向；验收脚本必须自行规避（已在脚本里记账，不改游戏键位） |

A 的修法：`ProductionRuntime.tick` 对 `blocked` 物品每帧在槽口**原地重试**交接，
不重置 `t`（画面不抖、读数仍是 blocked）；下游恢复后自动继续。B 只在脚本层规避，
因为改键位会动已验收的操作体验。

## 6. 结论

1. 接口盒可以做成**真实物品 + 真实安装状态 + 真实自动输入**，且不需要重构库存、配方、加工或运输系统；
2. 关键切口只有一处：`ProductionRuntime.handoff` 的「溜槽→机器」分支改为「必须经接口盒」；
3. 必须补两个东西才能满足验收：溜槽堵塞可恢复、加工核心可旋转；
4. 已按 §3 的决定执行；分流/合流、核心间物流、组合机械留待 P2-C/D。
