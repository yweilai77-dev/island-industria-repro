## 2. 关键架构决策（本阶段新增，均记录原因）

1. **唯一 GameRead 继续唯一**：所有新数据都进 `mechanical` 这一个 read —— 新增 `diagnostics`、`project`、`buildings`、`resources` 等只读字段（`tech` 沿 E1）。**没有第二个 read**（play harness 的 `play.advance` 依赖这一点）。
2. **UI 协议 v2**：后端 `game-ui-bridge/protocol.ts` 与前端 `frontend/frontend-ui-protocol.ts` 同步升到 2；state 增加 `tech/project/diagnostics/save`，命令增加 `tech/*`、`project/proof/*`、`save/*`。旧 v1 客户端被明确拒绝（仓库内已无 v1 发送点）；`__II_TEST_FLAGS__` 测试入口与正式 UI 走同一条协议。
3. **运行证明与物品交付是两个独立条件**：`tech.submit` 对项目节点永远不直接解锁（交满返回 `pendingVerification`），唯一完成路径是 `completeProjectNode`（要求交付全齐 + 运行证明守卫通过）。这样「先交齐再证明」「先证明再交齐」两种顺序都成立。
   - 偏差说明：E0 §6.6「终局整体交付、未完成前不扣料」被任务书 §五 C1「支持部分交付」覆盖 → 现在交满即扣料并处于「等待运行证明」；完成仍需两条件。
4. **诊断/终局服务只读、门控在服务入口**：`diagnostics.snapshot()` 在 `line-diagnostics` 能力解锁前返回 **null**（不是空数组）；数据只来自 `goalProgress` 观测 + `ports`/`assembly` 快照，不缓存第二份状态、不伪造运行状态。
5. **正式存档只有一套**：快照 v1（纯 JSON、~3.3 KB 中型工厂、512 KB 上限仅防损坏）。科技进度复用 E1 的 `serialize/restore`，不建第二套科技存档。存储通道在前端 realm（localStorage/平台 SDK），引擎侧只负责快照收集/应用。
6. **测试模式存档分档（兼容性修复）**：真实玩家 = persistent（自动读档 + 15 s 自动保存 + 页面隐藏保存）；带 `saveStorageKey` = isolated（隔离键，存档验收用）；**带任何 `__II_TEST_FLAGS__` 但没有 key = off（不读不写）**。旧验收脚本因此不再被上一次运行的自动存档污染；引擎侧同时去掉了「transport 注入即自动读」的隐式行为。
7. **批量加工不绕过状态机**：3 条批量配方走真实 `tickMachine`（多件产出、整笔扣料、输出缓冲/动力/断电恢复全部沿用）；材料当量与单件配方相同，只提升吞吐。
8. **配方身份 = `recipeId`**（E1 已建立）：UI、门控、存档都只认稳定 ID；新增配方一律追加在列表末尾。
