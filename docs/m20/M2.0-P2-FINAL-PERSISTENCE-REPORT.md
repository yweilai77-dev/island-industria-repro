# M2.0-P2-FINAL · 持久化与恢复报告（工作包 E）

- 阶段：M2.0-P2-E3
- 结论：**项目此前完全没有存档系统；本阶段落地了项目正式存档体系 v1（单快照、纯 JSON、全状态覆盖、容错与幂等恢复），科技进度不再「刷新即清零」。**
- 关键交付：`assets/save/`（8 个源文件）+ 各系统的 `snapshot/restore` + 前端存储通道与三档模式 + `scripts/p2e3-save-reload.mjs` 真实游戏回读验收。

---

## 1. 为什么这是「正式存档」而不是临时科技存档

- 实现遵循既有设计 `docs/design/SAVE-ARCHITECTURE.md`：快照 v1、只存逻辑数据、派生状态读档重建、平台存储通道放前端 realm。
- **只有一份快照、一个存储 key 体系**；科技字段是快照里的一个切片（复用 E1 的 `tech.serialize()/restore()`），没有第二套科技存档。
- 快照同时覆盖世界状态（玩家/库存/建筑/机械/动力/物流/加工/资源），否则「读档后继续生产」无从谈起。

## 2. 快照 v1 结构（顶层字段）

```jsonc
{
  "version": 1,                  // 快照版本；未来版本拒绝读取，旧版本走迁移
  "savedAt": "ISO-8601",
  "engine": "0.4.19",
  "player":   { "x", "z", "level", "yaw" },
  "inventory":{ "stacks": [{ "itemId", "count" }] },
  "hotbar":   { "slots": [...], "selected" },
  "resources":[{ "id", "amount", "depleted" }],
  "buildings":[{ "id", "kind", "gx", "gz", "rotation", "level" }],
  "floors":   [ /* 楼层结构：支柱/楼板/开孔/楼梯 */ ],
  "mechanical": { "nextPartId", "kitGranted", "parts": [{ "id", "kind", "gx", "gz", "rotation", "level" }] },
  "sources":  [{ "partId", "enabled" }],
  "ports":    { "ports": [{ "partId", "slotId", "moduleId", "itemId", "count" }],
                "links": [{ "id", "from", "to", "moved" }] },
  "production": { "machines": [{ "partId", "recipeId", "progress", "inputItem", "inputCount",
                                "outputItem", "outputCount", "producedTotal" }],
                  "chutes": [ /* 溜槽在途物品 */ ] },
  "tech":     { /* E1 TechState：version/mode/delivered/unlocked/trackedId */ },
  "goal":     { "baseline", "completed" },
  "endgame":  { /* 运行证明窗口：state/startedAt/elapsed/produced/baseline/passed/... */ }
}
```

- 实测体积：空快照 **445 B**；中型工厂（20 零件 + 2 建筑 + 2 楼层 + 2 接口盒 + 1 连接 + 4 矿点）**3.3 KB**；512 KB 上限只用于防御损坏数据。
- **不存派生量**：空间索引、支撑面、可通行面、动力解算、几何、视图实体、节点四态、材料剩余量、加工阻塞原因等全部读档后重算。
## 3. 恢复顺序与事务策略

```text
floors -> player -> inventory/hotbar -> resources -> buildings
  -> mechanical(parts + nextPartId + kitGranted)
  -> sources(启停) -> ports(接口盒安装/缓冲 -> MaterialLink)
  -> production(机器配方/进度/缓冲/在途)
  -> tech -> endgame -> goal
```

- 顺序由数据依赖决定：楼层是支撑面来源（先恢复才能在楼板上放机器）；机械先于接口盒/加工；终局恢复要读 tech 快照；订单最后（它的基线来自世界观测）。
- **逐切片容错**：任一切片失败只记录 issue 并继续；未知 itemId/零件 kind/节点/字段逐条丢弃；计数/时间钳制到合法区间；整包不可解析时保持当前世界并上报错误（不进入半坏状态）。
- **幂等**：连续 restore 结果一致；重复提交/重复完成不会重复扣料。

## 4. 版本与迁移

- 快照 `version: 1`。`decodeSnapshot` 永不抛异常：缺版本按 v0→v1 迁移（补默认值），未来版本拒绝读取并记 issue。
- 科技进度沿用 E1 的独立版本与修复规则（未知节点/物品丢弃、计数 clamp、前置闭包修复），与快照版本解耦。
- 终局切片自带 `version: 1`，缺版本/未来版本丢弃并记 issue。

## 5. 存储通道与自动保存

- 通道在**前端 realm**：优先 `globalThis.__II_STORAGE__`（测试注入），否则 `localStorage`；正式环境可换平台 SDK，引擎只负责快照 JSON。
- 默认 key：`island-industria/save/slot-1`；测试可用 `__II_TEST_FLAGS__.saveStorageKey` 隔离。
- 自动保存（真实玩家 persistent）：面板关闭、页面隐藏（visibilitychange）、科技提交成功、15 s 兜底。
- 自动读档：启动首个 state 后读一次；引擎侧**不再**隐式自动读（`setTransport` 只注入通道，不发起读），只有一个决策点。
- 新游戏：清存储 + 取消在途读取 + 抑制「清档前发出、之后返回」的陈旧读取，然后由前端 reload 进入全新世界。

## 6. 与测试模式的隔离（兼容性关键修复）

验收脚本共用同一浏览器 profile，而自动保存/自动读档会让「上一次运行的世界」污染下一次运行。本阶段把存档行为分成三档（`frontend/frontend-save-channel.ts` 的 `resolveSaveMode`）：

| 触发条件 | 模式 | 行为 |
|:--|:--|:--|
| 没有 `__II_TEST_FLAGS__`（真实玩家） | persistent | 默认 key；自动读档 + 15 s 自动保存 + 页面隐藏保存 |
| `__II_TEST_FLAGS__.saveStorageKey` 存在 | isolated | 用指定 key；行为同 persistent（存档验收用） |
| 有 `__II_TEST_FLAGS__` 但无 key（所有旧验收脚本） | off | **不自动读、不自动存、不响应可见性、科技提交后也不存**；`save/read` 回 `found:false`；页脚显示「测试模式：不写存档」 |

该修复让 E1/P2-B/P2-C/P2-D 的既有验收脚本重新回到「干净世界」语义，同时不影响真实玩家。
