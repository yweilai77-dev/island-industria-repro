# M2.0-P2-FINAL · 兼容性报告

- 阶段：M2.0-P2（E2 + E3）
- 基线：`5e5c99d`（P2-E1 最终 HEAD）
- 结论：**M1.8 生产链、P1 八步订单、P2-B 接口盒、P2-C 物流、P2-D 组合机械、P2-E1 科技核心的语义与验收断言全部保持；本阶段修掉的是一批「以前从没真正跑通」的隐藏缺陷，并在过程中发现并修复了一个会污染旧脚本的存档系统兼容性问题。**

## 1. 兼容策略

1. **不改已验收的求解语义**：动力网络、加工状态机、端口/物料连接、组合机械推导一行未改；新增能力只加在入口与只读投影上。
2. **唯一 GameRead**：所有新数据进 `mechanical` 的只读字段（diagnostics/project/buildings/resources），没有第二个 read。
3. **协议 v2 双端同步**：前端与引擎同一版本号；仓库内已无旧版发送点；测试入口与正式 UI 走同一命令。
4. **旧验收脚本继续以 legacy 兼容模式运行**（E1 建立），不修改其断言；本阶段对脚本只做两类改动：① 采集/投料等**输入时序**改成状态驱动（对 CDP 丢帧健壮，不改变断言语义）；② 修复脚本自身的缺陷（跨矿点采集、legacy 模式注册、reload 竞态）。
5. **存档行为对测试隔离**：真实玩家 persistent / 隔离 key isolated / 旧脚本 off（不读不写），见持久化报告 §6。

## 2. 本阶段引入并修复的兼容性事故（按严重度）

### C1 存档系统跨运行污染旧验收脚本（严重，已修复）

- 现象：P2-B/P2-C/M1.8 回归脚本在最终代码上出现「世界被上一次运行覆盖」的症状（投料后机器缓冲空、目标格被占、采集/走路异常）。
- 根因：存档前端默认 key + 启动自动读档 + 15 s 自动保存**无条件生效**，旧脚本没有隔离 key → 每次运行都恢复上一次运行的存档。
- 修复（双层）：
  1. **前端三档**：无 flags = persistent（真实玩家）；有 `saveStorageKey` = isolated；有 flags 无 key = **off（不读不写）**。
  2. **引擎去隐式自动读**：`setTransport()` 不再自动请求读档，只有显式 `requestRestore()` 才读。
- 验证：修复后旧脚本回到「干净世界」语义；`p2e3-save-reload` 使用 isolated 模式验证真实存读档。

### C2 锻压机输入缓冲小于配方整笔原料（严重，已修复）

- 现象：`forge-smelter`(7)/`forge-processing-core`(8)/`forge-flywheel`(12) 三条配方**永远无法开工**（整笔扣料被输入缓冲 6 挡住）。
- 影响：T2.3/T2.4/T3.2 实际不可完成，诊断能力永远解锁不了 —— 这是 E1/E3 报告里「能力已登记待消费」说法的真实反例。
- 修复：输入缓冲 6 → 12；新增 `assets/__tests__/recipe-capacity.test.ts`（每台机器每条配方的整笔输入/产出必须放得进缓冲）。

### C3 采集输入偶发丢帧（既有 flaky，已缓解）

- 现象：E1 已记录「m18c 采集偶发少采 1–2 个」；本阶段长脚本中放大到 20–30%（CDP 极短按键在某些帧丢整次事件）。
- 缓解：① 采集中再按 F 会**排队**一次（不再丢弃）；② 采集时长 3.0→2.5 s（给输入落帧留余量）；③ 验收脚本改为**状态驱动**（按目标库存补齐）并统一用 `hold(key,60ms)`。
- 说明：这是测试脚手架/浏览器输入时序问题，不是游戏逻辑缺陷；真实玩家按住/正常按键不受影响。

### C4 采集储量从 20/点 改为 60/点（有意的平衡变更）

- `IRON_ORE_MAX_AMOUNT` 20→60（总 240）；单点仍 ≤99，3D 矿石计数扩展为三位。
- 旧脚本的采集断言是「增量 ≥ 次数−1」的容错写法，储量提高不影响；`resource.test.ts`/`map-regression.test.ts` 的契约数值已同步。

## 6. 结论

- 既有系统的**语义**没有被本阶段改变；兼容成本集中在「玩家获得能力的时机」（科技门控）与「输入时序/资源数值」两类，全部有明确修复与证据。
- 本阶段最重要的兼容性发现是**存档系统会跨运行污染测试世界**，已用三档模式 + 引擎去隐式自动读根治。
- 所有旧验收脚本的核心断言保持原样；新增/修改处均在报告中逐条列出。
